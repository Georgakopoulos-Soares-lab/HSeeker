# R3.11: runtime and memory re-measured on the final code — evidence and response (2026-10-11)

## Hardware and protocol

- **Node:** TACC Lonestar6 interactive node, **AMD EPYC 7763**, 16 vCPUs (KVM), 31 GB RAM, Rocky Linux
  8.10 — the same CPU model, core count, memory and OS as the manuscript's benchmark node
  (`benchmarks/benchmark_comparison.md`: "AMD EPYC 7763, 32 GB RAM, 16 vCPUs, Rocky Linux 8.10").
  `lscpu`, `free` and `uname` are saved in `benchmarks/results_2026-10-11/`. Nothing else ran on the node
  during the measurements.
- **Code:** branch `rtr-2026-10-11` at `2211f4e` (shipped defaults: minimum arm 8, maximum arm 1000,
  maximum spacer 10, purity 0.90, mismatch 0.10, AT filter 0.80, homopolymer filter, greedy overlap
  removal, scoring on), C extension built with the default portable flags.
- **Protocol:** as published — the `hseeker` command-line tool with `-purity-rmq`, wall time and peak RSS
  from `/usr/bin/time -v`, three runs per point (`benchmarks/parallel_sweep.py --minrep 8 --runs 3`; whole
  genome and score mode by `benchmarks/results_2026-10-11/run_runtime.sh`).
- **Inputs:** hg38 chr1 (UCSC, sha256 `04ee6db2…`, 248,956,422 bp) and the hg38 primary assembly (chr1–22,
  X, Y, M; UCSC `hg38.fa.gz`, sha256 `86db5389…`, 3.15 GB).

## Results

**chr1, greedy (default), worker sweep** (mean of 3 runs; each run within 3 % of the mean):

| Workers | Wall (s) | Peak RSS (MB) | Speedup | Efficiency |
|---|---|---|---|---|
| 1 | 173.8 | 1,330 | 1.00× | 100 % |
| 2 | 89.6 | 1,335 | 1.94× | 97 % |
| 4 | 47.4 | 1,335 | 3.67× | 92 % |
| 8 | 26.7 | 1,334 | 6.51× | 81 % |
| 16 | **16.3** | 1,334 | **10.65×** | 67 % |

**chr1, score-based overlap selection, 16 workers:** 23.9 s (23.7, 23.8, 24.3), peak RSS 1,335 MB,
47,217 loci (greedy: 45,927 with scoring on).

**Whole hg38 primary assembly, greedy, 16 workers:** **204.5 s (3 min 24.5 s;** runs 204.9, 203.0,
205.6 s), peak RSS 2,296 MB (2,290–2,305), **559,601 loci**. The three runs gave byte-identical output.

**Published values (minimum arm 10, code of June 2026, no composition filters in the CLI then):** chr1
187.7 s with 1 worker and 25.2 s with 16 (7.45×), peak RSS 1,612–1,965 MB, 96,729 loci; whole genome
"~5 min" by linear extrapolation.

**Reading.** On the same hardware the final code is faster (16.3 s vs 25.2 s on chr1 at 16 workers),
uses less memory (1,334 MB vs up to 1,965 MB) and scales better (10.7× vs 7.5×), although the default now
reports shorter arms. Likely contributors (not measured separately) are the composition filters, which
reduce the number of candidates that reach the scorer, the batched scoring of the parallel scan, and the
memory fix of 2026-10-08. The whole genome takes
3.4 min, so the extrapolated "~5 min" was conservative; it is now measured.

## Response to R3.11

> Computational benchmarking should be made more reproducible and somewhat less promotional. … The
> authors should either run the complete hg38 genome or explicitly label the estimate as an
> extrapolation throughout. Raw benchmark commands, output files and timing data should also be
> deposited rather than being available only "upon reasonable request." …

We agree and re-measured runtime and memory on the final code and default settings, on the same hardware
as in the original benchmark (AMD EPYC 7763, 16 vCPUs, 32 GB, Rocky Linux 8.10), with three runs per point
and peak memory from `/usr/bin/time -v`. On hg38 chromosome 1, HSeeker took 173.8 s with one worker and
16.3 s with 16 workers (a 10.7-fold speedup), with a peak memory of 1,334 MB. Instead of extrapolating, we
ran the complete hg38 primary assembly: 204.5 s (3.4 min) with 16 workers and a peak memory of 2,296 MB,
reporting 559,601 loci; the three runs gave identical output. The optional score-based overlap selection
took 23.9 s on chromosome 1. All commands, raw timing output, hardware descriptions and input checksums
are deposited in the repository (`benchmarks/results_2026-10-11/`, `benchmarks/parallel_sweep.py`), and
the code, data and benchmark outputs will be archived on Zenodo at publication; the Data Availability
statement now says so instead of "upon reasonable request". We also moderated the wording of the
performance claims (see comment 12). We also re-timed the other tools on the same node on the same day:
with 16 cores, chromosome 1 took 45.0 s with Triplexator and 64.7 s with triplex (run in 16 parallel
processes), against 16.3 s for HSeeker; nBMST and NeSSie have no parallel mode and took 96.5 s and 295.7 s
on one core.

| Tool (version) | Cores | Wall time, s (mean of 3; range) | Peak RSS (MB) | Output on chr1 |
|---|---|---|---|---|
| HSeeker (final code, defaults) | 16 threads | **16.3** (16.3–16.4) | 1,334 | 45,927 loci |
| Triplexator 1.3.2, defaults (`-ds -rm 1 -p 16`) | 16 threads (OpenMP) | 45.0 (43.5–47.8) | 1,714 | 275,476 target sites |
| triplex 1.50.0, defaults (`benchmarks/triplex_benchmark.R`, 1-Mb windows) | 16 forked processes | 64.7 (63.2–65.7) | 660 per process | 81,906 hits |
| nBMST / non-B_gfa `a891b59`, mirror-repeat module only | 1 (no parallel mode) | 96.5 (96.2–96.9) | 866 | 147,222 mirror repeats (33,519 classified triplex) |
| NeSSie `dbe6cb2`, `-T`, k = 16–20 | 1 (no parallel mode) | 295.7 (one run) | 1,056 | 720,811 motif occurrences |

# R3.10 — overlap-removal rule: response text and the evidence behind it

**Status:** draft response, 2026-10-09 (DEC-10 default = longest arm; code includes Nikol's
inward extension, merged 2026-10-09).

## Reviewer comment (verbatim)

> The overlap-removal strategy may discard biologically relevant alternatives. The greedy procedure
> retains the candidate with the longest arm within overlapping groups, using shorter spacer length as a
> tie-breaker. It is not clear that longest-arm length is always the biologically optimal criterion,
> particularly when a shorter overlapping motif has a substantially higher predicted stability. The
> authors should justify this choice and compare it with alternatives such as selecting the
> highest-scoring candidate. Since the web interface apparently permits overlapping motifs to be
> retained, the manuscript should also explain which mode is recommended for biological analysis.

## Draft response

We thank the reviewer for raising this point. It made us look closely at what the overlap step
actually decides, and we agree that "longest arm" is not self-evidently the right criterion. We
have done three things in response.

**First, we implemented the alternative the reviewer suggests and compared the two directly.**
HSeeker now offers score-based selection alongside the longest-arm rule
(`overlap_strategy="score"`, `-overlap-strategy score`, and a matching option in the web interface).
In score mode, every candidate is scored first, and overlapping candidates are then resolved in
descending order of predicted stability, with ties broken by longer arm, then shorter spacer. We
compared the two rules on the benchmark and on human chromosome 1 (hg38):

- On the benchmark, the two rules never disagree about *whether* a sequence contains an H-DNA
  motif. The detection call is identical for every record under all 576 parameter and filter
  combinations we evaluated, so none of the reported performance figures depend on this choice.
- On chromosome 1, score-based selection keeps every locus found with the longest-arm rule:
  each of the 96,731 longest-arm loci is overlapped by a score-selected hit. In 83.7% of loci both
  rules report exactly the same motif. In the remaining loci, score-based selection reports a
  shorter, overlapping variant with a higher predicted stability. It also reports 1,075 additional
  loci (1.1%), mostly GA-rich mirror repeats adjacent to a longer motif that the longest-arm rule
  had absorbed. These are exactly the "biologically relevant alternatives" the reviewer had in mind.

**Second, we kept the longest-arm rule as the default, and we now explain why in the manuscript.**
Both rules locate the same regions; they differ only in which representation of a region is
reported. The longest arm describes the full extent of the mirror repeat, the region that can
participate in strand exchange, and it is a purely geometric criterion that does not depend on the
calibration of our stability score. As we acknowledge in response to R2.4 and R3.4, that score is an
experimentally informed heuristic rather than a calibrated free energy. We are therefore reluctant to
let fine score differences between overlapping candidates decide what a user sees by default.
Score-based selection also carries a cost at genome scale: chromosome 1 took 42.6 s instead of
25.9 s on 16 threads. We have also made the reported motif canonical: matching bases at the
spacer boundary are now moved into the arms, and identical arm/spacer representations are reported
only once.

**Third, we state which mode to use, and the web interface follows the same rules.** We added the
following guidance to the Methods and to the documentation:

- **Genome-wide annotation:** use the default (longest arm). It gives one non-redundant motif per
  region and is fastest.
- **Locus-level work,** such as choosing which variant to test experimentally or to design a
  construct around: use score-based selection. When candidates overlap, it reports the variant with
  the highest predicted stability.
- **Exhaustive or downstream statistical analysis:** disable overlap removal (`-skipoverlap`, or
  "Keep all raw hits" in the web interface). After the boundary normalisation above, this returns
  every distinct candidate without duplicate representations.

The web interface offers the same three options, with the same default. It now also applies the
same composition filters as the command-line tool, so results from both are identical for the same
settings.
